Introduction

Setting up sessions in PHP is a very important skill for secure web development. You may have heard about PHP, server sessions, and their importance, but we’re going to dive in and really explain why and how we can write code to use them.

Websites are often built on the simple backbone of the browser sending HTTP requests and the server responding with HTML. HTTP, and by extension HTTPS, is stateless. This means that servers don’t remember a visitor between requests, even ones seconds apart. PHP uses sessions to resolve this. The server stores the user’s data, and the browser holds a small cookie (named PHPSESSID) containing a session ID. On each request, the browser sends that cookie back, and the server uses the ID to find that user’s data.

PHP is a server-side language, used to run code on the server so that the user only sees the resulting HTML and not the PHP code itself. This is different from JavaScript code, which runs in the browser and can be seen by anyone with View Source. Sessions can be used across different languages, but we’ll demonstrate how sessions can remember information about a user between page loads in PHP. Without sessions, every time a page loads, the server acts as if it’s the first time you’ve ever visited the page. Sessions allow a page to remember your login status, your role or permissions, your shopping cart, and your progress through a multi-step form. Sessions should NOT store passwords or large pieces of data. Passwords are already verified at login, so storing them in a session only creates risk.

Let’s show how this is done by practicing writing PHP with a real-life example that will create a session to maintain the login status of a user!

PHP in 60 Seconds

PHP code always sits between the opening and closing tags <?php and ?>. Anything inside these tags runs on the server. This code itself isn’t visible to the browser; only the HTML that it produces is. Every variable starts with $, like $username. It’s just like creating a variable in Python with username = 'kyle123'; the most visible difference is the $. Also, unlike in Python, every PHP statement ends with a semicolon (;). Superglobals, which are vital to this tutorial, are built-in arrays that PHP fills in automatically so that you can use them anywhere in your code. $_POST and $_SESSION are two examples. The $_POST superglobal contains the data a form sent using the POST method. The $_SESSION superglobal contains the current user’s session data, and you can add your own values to it. With superglobals, you use square brackets to access a specific value in the array, for example, $_POST['username'].

Here’s what all of this looks like together:

<?php
$username = $_POST['username']; // get the name typed into the login form
$_SESSION['username'] = $username; // remember it for later pages
echo "Hello, " . $username; // the . joins text together
?>

For $_SESSION to work, the page must first call session_start(), which is exactly where we’re headed next.

Starting a Session

Every page that uses sessions begins by calling the session_start() function. On a first visit, session_start() creates a new session and sends the PHPSESSID cookie to the browser. After that, the browser sends the same cookie back with every request, and session_start() uses it to load the session variables that were saved earlier back into $_SESSION. That’s the moment the server actually “remembers” you.

There’s one catch: session_start() must be called before any HTML output, even a stray space or blank line before the <?php tag. The cookie travels in the HTTP headers, and headers have to be sent before the page content. If you call it too late, PHP shows a “headers already sent” warning, and the session won’t start. You’ll also need to call it on every page that uses $_SESSION, not just the login page; otherwise, that page can’t see the session data.

Here’s how the top of our login file begins:

<?php
// Must be the very first thing in the file, before any HTML output.
session_start();

Logging a User In

First, we read what the user typed into the login form:

$username = $_POST['username'] ?? '';
$password = $_POST['password'] ?? '';

The $_POST superglobal holds the username and password the user typed in, which the form sent using the POST method. We store those values in variables to use in the rest of the code. The ?? '' tells PHP to use an empty string if the user didn’t enter anything for either the username or password.

Then, we look up the user in the database:

$stmt = $conn->prepare("SELECT id, password FROM user WHERE username = ?");
$stmt->bind_param("s", $username);
$stmt->execute();
$user = $stmt->get_result()->fetch_assoc(); // null if no user was found

We use a prepared statement to write a SQL query that looks up the user with that username and fetches their stored password hash. The prepared statement separates the SQL command from the user input. The ? is a placeholder, and bind_param() sends the username to the database separately as plain data, so even if someone types SQL code into the username box, it’s never run as a command. This prevents SQL injection, an attack where someone types SQL code into a form to trick the database into running it.

Next, we check the password:

if (!$user || !password_verify($password, $user['password'])) {
    $_SESSION['login_error'] = "Invalid username or password";
    header("Location: ../views/login.php");
    exit;
}

We first check whether a user was found, and then we use password_verify() to compare the password the user entered with the hash (a scrambled version of the password that can’t be reversed) stored in the database for that username. The double pipes || are the “or” operator in PHP, so login fails if the username doesn’t exist or the password isn’t correct. In either case, an error message is stored in $_SESSION['login_error'] so the login page can display it after the redirect. The header() function then sends the user back to the login page, and exit ends the script. The error message is also generic, so malicious users can’t use a more informative message to enumerate accounts (figure out which usernames exist).

If the login succeeds, we give the user a new session ID and remember who they are:

session_regenerate_id(true);
$_SESSION['user_id'] = $user['id'];
$_SESSION['username'] = $username;
header("Location: ../index.php");
exit;

Here, the session_regenerate_id() function gives the user a brand-new session ID, and the true argument deletes the old session data. This protects against session fixation, an attack where someone plants a session ID they already know in the victim’s browser before login. Once the user logs in, that planted ID becomes useless. Next, we save the user’s information in $_SESSION. We store the user’s ID, not their password. The password was already checked, so there’s no reason to keep it, and leaving it in the session data on the server would expose it if that data ever leaked. Finally, the logged-in user is redirected to index.php, and the script ends.

Protecting a Page

<?php
session_start();
if (!isset($_SESSION['user_id'])) {
    header("Location: views/login.php");
    exit;
}
?>

The code above goes at the top of any page only logged-in users should see. The session_start() function loads the session so that the page can use the session variables. Then, isset() checks whether a user_id is stored in the session (the ! means “not”). If there isn’t one, the visitor never logged in, so header() redirects them back to the login page. Don’t forget the exit after the redirect: header() only tells the browser to go somewhere else, and without exit, PHP keeps running and still sends the rest of the protected page.

Logging Out

<?php
session_start();
session_unset();
session_destroy();
setcookie(session_name(), '', time() - 3600, '/');
header("Location: ../views/login.php");
exit;

To log a user out, we use a few more session functions. We’ve already talked about session_start(), which we still need here because you have to open a session before you can destroy it. Next, session_unset() clears the variables saved in the $_SESSION superglobal array, and session_destroy() deletes the session data stored on the server. The setcookie() function sets a cookie’s expiration time; setting it to a time in the past tells the browser to delete the PHPSESSID cookie. Finally, header() sends the user back to the login page.

Security Tips and Warnings

Security has come up at almost every step, so here’s a quick recap of the habits that keep sessions safe:

Regenerate the session ID at login. session_regenerate_id(true) gives the user a fresh ID, which blocks session fixation.

Use prepared statements. Sending user input to the database as plain data prevents SQL injection.

Keep error messages generic. “Invalid username or password” stops attackers from enumerating which accounts exist.

Never store passwords in the session. Store the user’s ID instead, since the password has already been checked.

Always exit after a redirect, so a protected page is never sent to someone who isn’t logged in.

Fully log users out with session_unset(), session_destroy(), and an expired cookie.

One more tip: PHP lets you set security flags on the session cookie. HttpOnly blocks JavaScript from reading it, Secure sends it only over HTTPS, and SameSite limits when it’s sent to other sites. You can turn these on with session_set_cookie_params() before calling session_start().

Additional Resources

PHP Manual: Sessions: The official PHP documentation for sessions, with a page for every session function used in this tutorial (and many more). It’s best used as a reference once you understand the basics.

OWASP Session Management Cheat Sheet: A guide to the best security practices for preventing session breaches, from OWASP, a nonprofit focused on web application security. It goes deeper into session fixation, cookie flags, and session timeouts, and it’s worth reading before building anything real.

MDN: Using HTTP Cookies: Mozilla’s beginner-friendly explanation of how cookies work, including the HttpOnly, Secure, and SameSite attributes. It’s helpful for understanding what the PHPSESSID cookie is actually doing.

W3Schools: PHP Sessions: Short, simple examples of starting, changing, and destroying sessions. It’s great for beginners, though it skips most of the security practices covered here.

Microsoft Azure: What Is a SQL Database?: An introduction to SQL databases and how they store data. It’s useful background if you’re new to the database side of the login code.

Microsoft Learn: SQL Injection: Microsoft’s explanation of how SQL injection attacks work and how to defend against them, including parameterized queries, the same idea as our prepared statements. Its examples use SQL Server, but the concepts apply to MySQL too.

Stytch: What Is an Enumeration Attack?: A plain-English overview of enumeration attacks, including how attackers use different error messages to discover valid usernames. It shows exactly why our generic error message matters.
